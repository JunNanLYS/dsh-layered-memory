# 蒸馏路由回退链：逐路由全额超时 + 空输出判失败

背景：Issue #31——慢 TTFT 路由（首包 20s+）× 上游网关 ~20s 静默掐断，蒸馏调用以
固定 20s 失败（`llm aborted`），单点路由没有退路，失败切片滞留未蒸馏缓冲；用户只能在
设置页手动来回切换模型当"人肉回退"。0.8.6 的按会话指数退避只放慢同一路由的重试
节奏，没有"换路由"这个自由度。

决定：

1. **链结构与条目形态**：主路由解析优先级不动（静态 pin > 设置页运行时选择 >
   默认模型），`llm.fallbacks` 对象列表（`{provider, model, reasoningEffort?}`）
   按序追加在后；与主路由或先前条目完全相同（provider+model）的条目跳过；
   provider/model 缺失的条目剔除。
2. **失败判定**：error/aborted finish、网络异常、空输出（流正常结束但 0 字符）
   触发降级；调用方 signal 主动取消不降级（取消不是路由故障，立刻上抛）；
   JSON 解析失败不触发（发生在调用边界之外，属于成功调用的输出质量问题）。
3. **每路由全额超时**：每次尝试新建超时信号，不做整链共享预算、不加每条目
   超时字段。
4. **条目档位三级优先**：运行时设置页档位（非空）> 条目档位 > 全局静态档位；
   无论来源仍过 decideSendableEffort 能力钳制（不支持就降级为不传 + 告警一次，
   能力缓存本就按 provider+model 键控，换路由自动生效）。
5. **尝试与退避分工**：每条路由每次调用至多一次，全部失败抛最后一个错误，
   重试节奏完全交给既有按会话指数退避（不在链内原地重试）。

理由：空输出对蒸馏必然报废（四个调用点全部把输出喂 JSON/Markdown 解析），返回
空串只是把失败推迟到下游且丢掉现场；逐路由全额超时是回退链的存在前提——Issue
的病灶正是"慢模型需要 60~100s 首包，网关 20s 掐断"，共享预算会让回退路由拿到
的窗口小于其真实 TTFT；对象列表而非 zip 平行数组（provider[]/model[]）是因为
长度不齐时语义无解，且条目要携带第三个字段（档位覆盖）。

## 考虑过的选项

- 整链共享超时预算：回退路由窗口缩水，慢 TTFT 场景下回退链失效。
- zip 平行数组（`provider: [a,b]` + `model: [x,y]`）：长度不匹配语义无解，
  加档位字段后更糟。
- 每条目 timeoutMs：同一部署里逐条配超时属 YAGNI，等真实需求再上。
- 按层路由（L1/L2/L3 各配各的路由）：方向成立但属独立特性，列路线图
  （#31 方案 2，后续功能）。
- fork-session 子代理蒸馏：破坏"LLM 输出操作 JSON / 工程侧执行"的架构边界与
  用量/成本记账钩子，否决（#31 方案 3）。

## 后果

- `callLLM` 空输出从"返回空串 + warn"改为抛错：蒸馏各层调用方的既有 catch
  路径天然兼容（管线失败只记日志不阻塞），未配置回退链的部署同样生效。
- 记账面（llm-usage / token_cost）按尝试粒度增长：失败尝试也计 failures 与
  当时流内用量，成功记实际服务路由——成本看板归因不因降级失真。
- 设置页"主路由 + 回退链"可视化编辑器（含运行时键形状设计：单模型键
  `distillProvider/distillModel` 如何演进成链）为后续独立任务，走 design spec
  循环；当前静态链不受设置页选择器抑制（链是部署者自己写的静态配置）。
