# FTS 防御性删除保持按 record_id 扫描，拒绝 rowid 映射

背景：每次 upsert 前的防御性 `DELETE FROM l1_fts WHERE record_id = ?` 因 record_id
在 FTS 表中 UNINDEXED 而退化为 O(N) 全扫（批量写整体 O(N²)；上游 MemoryCore 同款，
属忠实继承而非移植偏差）。改成"record_id → fts rowid 映射表"可变为索引定位，但引入
陈旧映射失效模式：FTS 重建后映射未同步重置 → 按陈旧 rowid 删错行 → 其他记录的全文
索引被静默清掉，无报错无日志。**静默错删比慢更糟。**

决定：保持现状不动（十万条级记忆的用户罕见，未出现真实瓶颈）。若将来出现写放大
瓶颈，正确修法是 FTS5 外部内容表（`content=` + 触发器）——映射随内容表结构性同步，
没有独立状态可以变陈旧。tokenizer 戳触发的 FTS 全量重建是现成的自愈通道。

## 考虑过的选项

- rowid 映射表：拒绝。要堵死陈旧映射需要同事务原子性 + 全部 drop/重建路径同步重置
  + 迁移用版本戳判断三道防御，为罕见规模的收益引入这套不变量不值。
- 外部内容表 + 触发器：正确修法，但属 schema 迁移，留待有真实需求。
- 删除前主表点查预判（仅当行已存在才执行 FTS 删除）：**已采纳**。判断依据是主表现状、
  不维护派生状态，陈旧映射顾虑结构性不存在；rebuild / reindex / 旧库导入等"全新增记录"
  路径的 O(N²) 写放大就此消失（这正是重建按钮对中等库用户的隐藏成本）。
