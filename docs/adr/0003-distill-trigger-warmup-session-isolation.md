# 蒸馏触发：渐进阈值 + 全链路会话隔离

背景：现状 `minMessages=1` 每轮必触发抽取（每轮 1-2 次后台 LLM 调用）。上游原版是
每 5 轮触发 + warmup 爬坡（1→2→4→稳态）+ 闲置兜底，且其管线状态按 sessionKey 键控。
查证发现我们的移植存在走样：pending 桶按族全局混装、背景消息是全局单数组——
跨会话污染在现状下已经存在（会话 A 的消息给会话 B 的抽取当背景）。

决定：

1. **渐进阈值**：蒸馏触发阈值从 1 起步，每次成功抽取后翻倍至稳态值
   （`minMessages` 语义升级为稳态阈值，默认 6 条消息 ≈ 3 轮）。爬坡状态按档位桶
   （auto/chat/work）各记一次，随 pending.json 持久化（档位是触发维度，语义上等价于
   按族记一次——纯档一一对应族，auto 覆盖两族）。
2. **会话隔离五通道**：pending 条目携带 sessionId；阈值按会话计数、只抽取该会话
   切片；闲置兜底按会话跟踪（全局定时器 tick，静默 ≥300s 的会话清切片，活跃会话
   继续攒）；背景消息废弃全局内存数组，抽取时按 sessionId 现查 L0（跳过切片自身
   防抽取目标混入背景）；失败重试残留随 sessionId 归属原会话。
3. **档位切换同步**：非 off 档之间切换 → 该会话切片立即按**捕获时档位**蒸馏
   （不重贴标签——档位是蒸馏透镜，换透镜抽取等于改写语义归属）；切到 off →
   切片挂起不蒸馏（尊重"停止记忆"意图）；从 off 切回 → 挂起片按捕获档位清掉。

理由：爬坡兼顾新用户"首轮出记忆"与稳态攒批省调用；闲置兜底接住"没攒够阈值用户
就离开"的尾部（新鲜度损失有界）；会话是记忆语义的自然边界，跨会话混装会污染
情境链与场景归属。

## 考虑过的选项

- 固定 minMessages=1（现状）：最新鲜但每轮双调用，费。
- 固定阈值无爬坡：省但冷启动慢，新用户首轮无记忆。
- 按会话各自爬坡：需会话维度的爬坡状态与清理，个人工具不值。

## 后果

- pending.json 持久化 schema 增加 sessionId 字段；旧数据无字段的归一组"legacy"
  一次性蒸馏，向前兼容。
- session-modes 的 set() 挂档位切换回调通知 runner，不新开事件总线。
- L0Store 新增按会话取最近消息的访问器（走 idx_l0_session_id 索引）。
- 全局 background 内存数组移除（顺带修掉现存跨会话污染与重启丢背景两个缺陷）。
